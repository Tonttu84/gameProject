`docs/CAMPAIGN_PLAN.md` under their own ids (M-*, S*-*, C-*, E-*, SB-*). One row per decision.
Never rewrite an old row: a reversal is a new row that names the one it replaces.

| D10 | The campaign server's JWT `SECRET` and dev login (`DEV_USER`, `DEV_PASSWORD`) leave the code for the secrets repo's `gameproject/dev.env` overlay, with fresh random values (the old committed ones stay in history, retired). The committed `dev.env` keeps the names with empty values; docker compose loads both, `make serve`/`server-node` load the overlay through `scripts/with-dev-env.sh`. Without the overlay the server still starts: a missing `SECRET` becomes a random per-process secret and a missing login turns the dev login off, each with a `config:` boot warning. No production hard error is added: there was none before (the image sets `NODE_ENV=production` and is also the local `docker-up` stack). The CI smoke seeds a throwaway login per run. Owner-approved 2026-11-11; the no-overlay behaviour as the owner set it. | The shared rules keep values out of projects and let a project run without the overlay with the affected features off, said plainly. A random secret only costs logins on restart; any fixed fallback is a value someone can read. | A hardcoded fallback; refusing to start without the overlay; a test-only password committed for the smoke. |

| D12 | The 2026-11-11 Dependabot fix (critical and high alerts, owner-approved) takes vitest to `^4.1.12` in `campaign-server/` and `frontend/`, not the `^5.1.0` of Dependabot PR #14. | D13 | The embedded mongod (`utils/db.js`, and `tests/helpers/db.js` through the same constant) is pinned to MongoDB 7.0.24 instead of following mongodb-memory-server's default, taken with mongodb-memory-server 11 and mongoose 9 from Dependabot PR #15 on 2026-11-11. A test ties the pin's major to the `mongo:` image in `docker-compose.yml`. The version lives in `campaign-server/package.json` (`config.mongodbMemoryServer.version`), which the package's postinstall download reads, and the code reads it from there and passes it explicitly. Agent's choice. | mongodb-memory-server 11 moves its default binary from 7.0 to 8.2, and mongod 8.2 refuses a data dir whose feature compatibility version is 7.0: started on a copy of an existing `~/.gameproject/db` it exits with code 62, while 7.0.24 opens it. 7.0 is also the server docker-compose and CI run (`mongo:7`), so tests now run the server CI runs and one binary is downloaded, not two. Moving to 8.x is a data-dir upgrade (7.0 to 8.0, `setFeatureCompatibilityVersion`, then 8.2) for its own change. The package.json setting alone is found only from the current directory, so a server started from the repo root would miss it; the code pin alone leaves `npm ci` fetching 8.2 and the first test run downloading 7.0 inside a 30 s hook, which timed out here. The postinstall looks for the setting from `INIT_CWD`, which `npm install --prefix campaign-server` leaves at the repo root, so the Makefile's `campaign-server/node_modules` rule (behind `serve`, `server-node` and `balance-sheet`) now installs from inside `campaign-server/`; an install run by hand with `--prefix` from the root still fetches 8.2 and is a wasted download, not a broken server. | Holding mongodb-memory-server at 10 (its 7.0.24 default is the same pin, left implicit); only one of the two places. |
| D14 | jsdom stays at 26 in `frontend/`, not the 31.0.0 of Dependabot PR #15, and Dependabot ignores jsdom `>=30`; vitest's semver-major updates are ignored too (D12). Both ignores sit in `.github/dependabot.yml` and go when the local Node moves to 24 LTS or 26. Agent's choice, 2026-11-11. | jsdom 30 and later declare `engines.node` `^22.22.2 \|\| ^24.15.0 \|\| >=26.0.0`, so with `engine-strict=true` `npm install` refuses Node 25, which the owner's Windows machine runs; jsdom 27 to 29 still allow `>=24.0.0`, so the version range keeps them coming. Every vitest 5 release refuses Node 25, so a semver-major ignore is exact there. For security updates the two rules differ: per GitHub's docs `ignore` rules also hold security updates, but `update-types` affects version updates only, so a vitest security fix that needs 5.x still arrives as a security pull request (one that fails `npm install` on Node 25), while one that needs jsdom 30 or later is held by the `versions` range. | Taking jsdom 31 (breaks `npm install` locally); a semver-major ignore for jsdom, which would also block 27 to 29; dropping `engine-strict`, which guards the lockfile (`.npmrc`). |
